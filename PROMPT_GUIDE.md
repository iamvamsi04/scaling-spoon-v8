# Detailed billing-agent instructions

Updated October 15, 2026 in version_6_latest.

Admin instructions now prefer billing_analysis for invoice trend charts, with explicit period, metric and filters. Order totals use charged_price; only explicitly net/refund-adjusted requests subtract refunds. Custom SQL must aggregate at the requested grain, resolve currency before grouping and repair correctable chart errors in the same turn. Chart attachments are validated locally and supplied independently of the final model text. Month/year temporal labels are accepted locally without another model call.

All required model calls retain the full instructions. The experimental compact-answer stage was removed after live logs showed it added an extra inference. Existing local reply parsing handles supported output formatting without a separate formatting model call.

Both modes now receive the actual SQL table/column map and foreign-key join keys before inference, generated by mcp_server/tools/database.py and scoped to the mode. The agent can locate fields such as product_details.category and order_details.currency before choosing SQL. Schema-related SQL failures return the map for correction. The shared chart contract also accepts long-form grouped bars/lines/areas with x, group and exactly one y measure.

The application assembles its system instructions from the files below. These are the actual prompts loaded by BillingAgent, not a separate sample prompt to paste elsewhere. Restart the API after replacing/updating the files.

## Customer mode

Customer instructions combine the role, conversation, shared task, reply and memory policies. Actual memory adds customer-specific data.

1. agent/system_message.py: role, grounded answers, customer scope, ten customer tools, complete product discovery, price/feature evidence, budgets, business actions, invoice/refund limitations, schema and the final response boundary.
2. agent/conversation_policy.py: twelve-stage flexible store playbook, from greeting and discovery through product selection, complete quotes, draft changes, checkout, invoices and complaints.
3. agent/task_policy.py: shared tool composition, SQL safety, coverage/counting, product queries and pagination, pricing, attributes/relationships, financial aggregation, failure recovery and admin-only chart rules. It also appends the existing detailed 25-type chart contract.
4. context/reply_text.py (REPLY_POLICY): user-visible plain-English style and the distinction between the visible reply and the internal response envelope.
5. agent/shopping_policy.py: persistent preferences, product references, pagination, pending proposals, supported memory patch fields and exact final-output requirements, followed by saved memory.

Customer-mode final model output must be exactly one valid JSON object with reply and shopping_update. All visible prose belongs inside reply once; no prose or Markdown fence may surround the object. The application displays only reply and handles the memory patch internally. The existing mixed-response cleanup remains in use for malformed model behavior and historical saved messages.

## Admin mode

agent/admin_message.py replaces the customer role/playbook. Shared task and visible-writing instructions still apply. Admin final output is plain English, without a customer JSON envelope or shopping-memory update. Only execute_sql_query, billing_analysis, billing_anomalies and download_invoice are available; the mode remains read-only.

## Practical examples addressed by the instructions

- What all products do you have: complete count/category overview, rather than an arbitrary five-row sample.
- List all products / next page: counted product pages with saved filters, page scope and current prices.
- Which product is better / anything cheaper: recorded needs, exact features, stock, quantity and honest unknowns.
- Under a budget: distinguish per-item, total merchandise and all-in checkout budgets.
- Make it two / swap this item: preserve every basket line, show the complete replacement and confirm it.
- Yes, but change the product: treat the change as a new proposal, not approval of the old purchase.
- Where is my invoice / why did I pay this price: use owned historical billed lines and actual discounts/tax/shipping.
- Refund this: verified placed order, exact amount/reason, explicit approval and accurate local-ledger wording.
- I already paid / when will my refund arrive: explain the missing external payment evidence without inventing balances or timing.
- Show store-wide analytics as a chart: correct mode, full aggregation, currency separation, actual supported chart artifacts and bounded complete data.
- Tool failure / timeout after a write: verify state and avoid unsafe duplicate actions.
- Prose followed by a JSON reply: one final envelope and one displayed answer.

## Limits and verification

A detailed prompt improves instructions; it does not guarantee arbitrary model behavior or replace tool authorization, database checks, output cleanup and confirmation handling. The existing runtime protections remain necessary. Longer instructions add input tokens and can increase Azure processing time/cost. Live interpretation and latency must be evaluated with the configured Azure deployment; local integration tests use replayed model outputs while real application/MCP/database/UI code runs.

See TESTING.md for the checks completed for this update and CHANGED_FILES.md for the exact changed files.

## Product query instructions

Product discovery uses qualified, parameterized SQL against existing tables with complete counts and stable pages. product_query contains the last successful item query and its parameters, so navigation can resume without a dedicated browsing interface. The separate tool option is removed. All questions use the configured model and these prompts; there is no fixed-SQL application shortcut. Restart the API to load the changes.

## Mode-specific prompt loading

Customer mode uses CUSTOMER_TASK_POLICY, which preserves the shared rules through failure recovery and replaces the admin-only chart contract with a short prohibition. Admin mode retains TASK_POLICY and the complete chart contract. Customer query-tool schemas omit the unsupported chart argument and its instructions. Product pages can combine their matching count with the page rows using COUNT(*) OVER(); empty pages require a separate matching count.

See PERFORMANCE.md for timing logs, the optional reasoning setting and measured prompt-size reduction. No model or reasoning downgrade is enabled by default.
